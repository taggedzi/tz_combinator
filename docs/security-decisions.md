# Security decisions

This document records security decisions whose rationale is easy to lose when
the implementation or user interface changes. It is intentionally separate
from the operational security guidance so that the reasoning, trade-offs, and
responsibility boundaries remain visible.

## Raw output and terminal controls

**Status:** accepted

**Decision date:** 2026-08-06

### Context

Combinator accepts text that may be supplied by another person or system and
can emit text, CSV, TSV, NUL-delimited, or JSON Lines output. The text and NUL
formatters preserve values verbatim and append delimiters. CSV and TSV quote
their structural fields, but a quoted field can still contain bytes that a
terminal interprets as control sequences. JSON Lines serializes C0 controls
inside JSON strings.

Consequently, a hostile value can have two different effects depending on the
destination:

- In a delimiter-based consumer, a value containing the record delimiter can
  create an apparent additional record.
- On an interactive terminal, ANSI/OSC and related control characters can
  change terminal state or presentation.

The CLI is not a sandbox. A caller who controls the process environment,
command line, shell wrapper, executable, or output pipeline can already choose
another command, redirect output, or write terminal bytes directly. The
utility cannot determine whether a caller's claim that input is trusted is
correct.

### Options considered

1. **Escape every raw output value.** This would make terminal display safer,
   but would change the established text/NUL byte contract and break legitimate
   scripts that intentionally consume exact raw output.
2. **Reject raw formats for every destination.** This would prevent misuse, but
   would unnecessarily block trusted file and pipe workflows, including tools
   that deliberately use delimiter-oriented output.
3. **Rely only on documentation.** This preserves compatibility, but leaves a
   predictable terminal hazard for the common case where a user accidentally
   displays untrusted output.
4. **Guard interactive terminals by default, preserve redirected output, and
   provide an explicit opt-out.** This protects the common accidental-display
   case while retaining trusted use cases.

### Chosen policy

Combinator uses option 4:

- When raw text, CSV, or TSV output is going directly to an interactive
  terminal, the CLI scans normalized values and applicable formatting inputs
  before generation. Control characters cause `UNSAFE_TERMINAL_OUTPUT` before
  any record is written.
- NUL output is rejected for an interactive terminal by default because it is
  a machine-oriented format.
- JSONL remains the recommended format for untrusted records and subprocess
  integration.
- Output redirected to a pipe or file retains the established raw bytes. The
  receiving program is responsible for parsing them safely and must not replay
  hostile raw bytes to a terminal.
- `--allow-unsafe-terminal-output` is an explicit opt-out for trusted, local
  use cases such as terminal-control testing, reproducing an existing byte
  stream, or compatibility with a workflow that intentionally emits raw
  controls. Enabling it means the caller accepts responsibility for the input
  and destination.

### Responsibility boundary

The tool's responsibility is to provide a safe default, make the unsafe mode
deliberate and discoverable, preserve documented compatibility, and explain the
residual risk. The user's responsibility is to verify input provenance and use
JSONL or a suitable parser when processing untrusted records. A user who
intentionally enables the override, or routes raw output through a terminal
writer, has chosen to disable that protection.

This is defense in depth, not a claim that Combinator can secure an untrusted
shell or operating environment. If an attacker controls the invocation or
environment, they can bypass a terminal check with ordinary process and shell
facilities regardless of whether this option exists.

### Review trigger

Revisit this decision if a future release changes the raw output contract,
adds a structured output mode that does not escape terminal controls, or gains
an embedding/service boundary where the caller cannot reliably control the
output destination and input provenance.

## Content-preserving CSV/TSV and downstream interpretation

**Status:** accepted; implementation planned

**Decision date:** 2026-08-06

### Context

Combinator can receive data from logs, files, command-line values, services,
or other sources that may be controlled by a different trust domain. Encoding
that data as CSV or TSV changes its representation, but does not make the data
trusted. A report generated by a trusted process can therefore carry content
chosen by an untrusted producer.

CSV and TSV quoting protects structural boundaries such as fields, records,
delimiters, quotes, and embedded line endings when both sides use compatible
parsers. It does not neutralize the meaning that a later consumer assigns to a
field. Depending on that consumer and its configuration, preserved content may
be treated as a spreadsheet formula, typed value, expression, markup, command
argument, path, URL, or template input. A correct data-only importer may keep
the same content inert, while an unsafe loader or a later export can introduce
a second interpretation boundary.

Spreadsheet formula injection is one known instance of this broader problem,
catalogued as [CWE-1236](https://cwe.mitre.org/data/definitions/1236.html).
It is not the complete downstream threat model. Conversely, the presence of a
formula-like prefix does not prove that every consumer will execute it.

Combinator cannot reliably infer the destination, distinguish trusted from
untrusted values, or implement a universal sanitizer for all possible
consumers. The same value can be required exact data in a database pipeline
and active syntax in a spreadsheet. A transformation that protects one
consumer can corrupt data or create a new interpretation in another. Current
[OWASP CSV injection guidance](https://owasp.org/www-community/attacks/CSV_Injection)
likewise warns that there is no universal CSV sanitization strategy for every
spreadsheet application and downstream consumer.

### Trust boundary

Trust follows field content through conversion:

```text
untrusted producer -> input -> Combinator -> CSV/TSV -> downstream consumer
       untrusted       untrusted          untrusted field content
```

The fact that Combinator or another trusted system created the output file
must not be treated as evidence that every field is trusted. The destination
consumer remains responsible for interpreting, validating, or constraining
the field according to its own grammar and security boundary.

### Options considered

1. **Silently neutralize suspicious values in every CSV/TSV record.** This
   could reduce risk for a selected consumer, but it would make the formats
   lossy, change established output bytes, damage round trips and statistics,
   and still could not guarantee safety for unknown consumers.
2. **Reject CSV and TSV whenever input might be untrusted.** Combinator cannot
   determine input provenance, and this would remove legitimate database,
   analytics, interchange, and automation uses.
3. **Treat correct CSV/TSV quoting as complete safety.** This confuses
   structural serialization with downstream interpretation and leaves a
   foreseeable hazard undisclosed.
4. **Rely only on documentation.** This states the responsibility boundary but
   gives users no actionable protection when Combinator recognizes a common
   active-content pattern.
5. **Preserve raw formats, document the general boundary, and add narrowly
   defined warning and rejection controls for recognized risks.** This keeps
   lossless interchange while making a known hazardous workflow visible and
   controllable without claiming universal sanitization.

### Chosen policy

Combinator uses option 5:

- CSV and TSV remain content-preserving interchange formats. Structural
  quoting must not silently rewrite field values.
- Documentation and interface help must state that CSV/TSV protects structure,
  not the semantics assigned by downstream consumers, and that output derived
  from untrusted fields remains untrusted.
- Runtime detection may cover narrowly specified, testable patterns such as
  formula-like field prefixes. Its names and messages must describe that
  limited scope and must not promise that arbitrary downstream content is
  safe.
- CSV/TSV generation will offer `allow`, `warn`, and `reject` policies for
  recognized formula-like fields. `warn` is the default; `allow` explicitly
  accepts content-preserving output without that warning; `reject` fails
  before records are written or a destination is created or replaced.
- `allow` and `warn` preserve identical data bytes. Warnings go only to the
  diagnostic channel, never into generated data, and never include hostile
  field contents.
- General downstream guidance and specific runtime detection are separate.
  Combinator will not introduce a flag named `safe`, `sanitize`, or equivalent
  unless its exact destination, transformation, limitations, and data-loss
  behavior are defined.
- A future destination-specific export, such as a spreadsheet format with
  explicitly typed text cells, requires its own design and test matrix.

### Responsibility boundary

Combinator is responsible for structurally correct serialization, predictable
content preservation, clear security contracts, safe diagnostic handling, and
narrow controls for risks it can recognize. It is also responsible for not
describing output as universally safe when safety depends on a later
interpreter.

The caller is responsible for knowing or constraining the eventual consumer,
selecting the corresponding policy, and validating untrusted fields against
that consumer's grammar. A downstream component that constructs SQL, shell
commands, HTML, templates, paths, URLs, or other active content must apply the
controls required by that specific sink.

This division is not an attempt to make the product "idiot proof." It preserves
legitimate lossless uses while preventing conversion by a trusted utility from
silently implying that hostile content has become trusted.

### Disclosure decision

The current raw serializer behavior is not, by itself, a universal
neutralization defect: content-preserving CSV/TSV utilities generally cannot
secure an unknown downstream interpreter. The missing destination warning and
policy controls are treated as security-relevant product hardening and will be
implemented through the normal change and release process.

Reconsider a private or published security advisory if the project promises a
destination-safe export, automatically delivers attacker-controlled reports
across a user boundary, or receives evidence of confidentiality, integrity,
or execution impact in a supported workflow.

### Review triggers

Revisit this decision if Combinator adds a typed spreadsheet format, changes
the byte-preservation contract of CSV/TSV, adds new active-content detectors,
automatically opens or delivers generated output, or learns the destination
well enough to enforce a stronger consumer-specific policy.
